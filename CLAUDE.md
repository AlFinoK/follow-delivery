# follow-delivery

MVP-трекер доставки грузов для Leader Trans Team. Двуязычный (RU/KZ), одна публичная страница поиска + защищённая админка.

## Стек

- Next.js 16 (App Router) + React 19
- Prisma 6 + PostgreSQL
- NextAuth 4 (Credentials provider, JWT-сессия)
- Tailwind CSS 4
- react-day-picker 9 + date-fns 3

## Запуск

```bash
npm run dev      # next dev
npm run build    # next build
npm run start    # next start
```

`postinstall` запускает `prisma generate`.

## ⚠️ Ловушки и неочевидные конвенции

### 1. Переименование `id` ↔ `docId` в API-ответе

`mapCargo` в [lib/mapCargo.ts](lib/mapCargo.ts) (общий для `/api/cargos`, `/api/cargos/[id]` и `/api/folders/[id]`) меняет местами:

- `cargo.id` (Prisma cuid) → `docId` в JSON
- `cargo.trackingId` → `id` в JSON

То есть на фронте:
- `cargo.id` = публичный трек-номер `"CARGO-..."`
- `cargo.docId` = primary key для `PATCH /api/cargos/[docId]` и `DELETE`

**Публичный поиск** (`GET /api/cargos?trackingId=`, без сессии) отдаёт урезанный `mapPublicCargo`: без `docId`, `folderId`, `folderName`, `cargoNumber` — публичной карточке они не нужны. Сумма и статус оплаты остаются: их показывает карточка клиенту (решение продукта).

### 2. Статусы хранятся по-русски в БД

`Cargo.status` принимает только три значения, и они кириллицей:

- `"ожидает отправления"` (дефолт)
- `"в пути"`
- `"прибыл"`

Перевод на казахский/UI-лейблы — на стороне UI через `t('statusWaiting'|'statusInTransit'|'statusArrived')`. Сравнения в коде идут с русскими строками: `cargo.status === 'в пути'`.

Аналогично:
- `paymentStatus`: `none | partial | full`
- `currency`: `KZT | RUB`

В БД это обычные строки (не enum), поэтому допустимые значения проверяет сервер: [lib/cargoInput.ts](lib/cargoInput.ts) для грузов и массовый PATCH папки — иначе `400`. `cargoNumber` в БД не уникален, но API не даёт занять номер, который уже есть у другого груза (`409 «Номер уже занят»`; это проверка до записи, не ограничение БД).

### 3. Формат `deliveryTimeframe`

Строка `"NUMBER|UNIT"`, где UNIT ∈ `days | weeks | months`. Например `"10|days"`, `"2|weeks"`. Распаковка — `displayTimeframe()` в [lib/format.ts](lib/format.ts).

### 4. Генерация trackingId на клиенте

В [components/admin/NewCargoForm.tsx](components/admin/NewCargoForm.tsx):

```ts
'CARGO-' + Date.now() + '-' + Math.random().toString(36).slice(2, 11).toUpperCase()
```

Перед отправкой нормализуется `.toUpperCase().trim()`. При создании `currentCity = fromCity`.

### 5. i18n

- Свой `LangContext` ([contexts/LangContext.tsx](contexts/LangContext.tsx)) с `t(key)` и `tf(key, params)` для интерполяции `{key}` в строке.
- Состояние `lang` (`'ru' | 'kk'`) в `localStorage['lang']`; `<html lang>` синхронизируется с ним.
- **`t`/`tf` мемоизированы по `lang`.** Раньше они пересоздавались на каждый рендер, и любой `useCallback(..., [t])` перезапускал загрузку данных при смене языка (а у пользователей с сохранённым `kk` — дважды при открытии): страница шаблонов теряла недозаполненную форму. Не класть `t` в зависимости загрузчиков данных без нужды.
- `tf` подставляет все вхождения `{key}` и не интерпретирует `$&`/`$'` в значениях (`interpolate` в [format.ts](lib/format.ts)).
- Словари в [lib/i18n.ts](lib/i18n.ts) — два словаря (`ru`, `kk`) под типом `Translations`. При добавлении ключа править оба + тип.
- **Переведён весь интерфейс, включая админку** (накладные, шаблоны, папки, калькулятор, уведомления) — 481 ключ (2026-10-22; неиспользуемые вычищены). Новый текст в компонентах не хардкодить: только `t()`/`tf()`. Русскими остаются намеренно: **PDF накладной** (решение заказчика — документ только на русском, см. §11), **текст уведомления клиенту** (тот же принцип, см. §12), значения в БД (статусы, города), реквизиты в [company.ts](lib/waybill/company.ts) и формат сводки логистам в [model.ts](lib/waybill/model.ts) (зафиксирован заявкой №2782).
- **Валидация накладной возвращает КЛЮЧИ, а не текст**: `WaybillError = { step, key }` в [model.ts](lib/waybill/model.ts), тост показывает `t(err.key)`. Иначе казахский оператор видел бы русские ошибки. Серверная проверка в [mapWaybill.ts](lib/mapWaybill.ts) — последний рубеж (у API нет языка сессии), её сообщения остаются русскими и в норме недостижимы: клиент валидирует те же поля раньше.

### 6. Тосты между навигациями

**Вид и место — одни на весь проект** ([Toast.tsx](components/Toast.tsx), образец — артефакт «Тосты Leader Trans Team»): тост залит цветом статуса целиком — `success` зелёный, `error` красный, `warning` янтарный с тёмным текстом, `info` графитовый; цвета одинаковы в обеих темах. Контейнер — константа `TOAST_VIEWPORT`: снизу по центру, `z-[70]`, с учётом безопасной зоны телефона, пустое место пропускает клики. Новую страницу с тостами оборачивать в `<div className={TOAST_VIEWPORT}>`, свои `fixed top-4 right-4` не заводить.

Локальные тосты — массив в state + setTimeout; id тоста — `newToastId()` из [Toast.tsx](components/Toast.tsx) (не `Date.now()`: несколько тостов за миллисекунду давали одинаковые React-ключи). Для переноса тоста между переходами роутера используется `sessionStorage['pendingToast']` (JSON `{message, type}`), который читается на новой странице. Так переносятся «Груз создан! ID: …» (создание груза → `/admin`) и «Накладная сохранена» (правка → карточка).

⚠️ **Смена только query-параметров не пересоздаёт страницу** (Next ключует страницу без search params). Поэтому `WaybillDetailPage` читает `pendingToast` не только при монтировании, но и при выходе из `?edit=1` — иначе тост «застревал» и всплывал потом на другой странице.

### 7. Города

В [components/admin/Selects.tsx](components/admin/Selects.tsx) — захардкоженные `CITIES_KZ` и `CITIES_RU_LIST`. Опция «✏️ Другой город» переключает в режим свободного ввода.

### 8. Mock loading delays

Страницы намеренно держат `PageLoader` минимум 444 мс (`/admin/cargo/[id]`, папки, калькулятор, шаблоны) или 2000 мс (`/`) ради плавности UX. Список `/admin` вместо этого показывает скелетоны карточек. Повторные загрузки (смена вкладки/страницы, после сохранения) — «тихие», с маленьким индикатором, без полноэкранного лоадера. Логика — `minLoadDone` флаг + `setTimeout`. Не убирать случайно при рефакторинге.

### 9. SSR/CSR-расхождение

Из-за i18n из `localStorage` все клиентские страницы используют `'use client'` + `mounted`-флаг + `suppressHydrationWarning` на html/body и корневых div. Серверных action / RSC-форм нет.

### 10. Калькулятор: надбавка по областям, мин-тариф, пресеты (improves.docx + improves2.0)

- **Региональная надбавка** — [lib/calculator/districts.ts](lib/calculator/districts.ts). `resolveSurcharge(name, region)` → ДОЛЯ (0.2 = +20%): базовая ставка по округу (`DISTRICT_DEFAULT_SURCHARGE`: central/south/volga/ural 20%, caucasus 25%, northwest/siberia/fareast 0) + переопределения по областям (`REGION_SURCHARGE`). Ключевые правила improves2.0: Крым/Севастополь +30%; СЗФО по областям (Архангельская +35%, Мурманская +25%, Вологодская +20%, Псковская +15%, Ленинградская/Новгородская +10%); в Уральском и Центральном ряд областей — исключения с базовой ставкой 0% (Свердловская/Челябинская/Курганская/Тюменская; Московская/Орловская/Рязанская/Тверская/Тульская/Калужская/Липецкая/Ярославская/Костромская/Ивановская + Москва). `resolveDistrict` остался для подписи округа. ⚠️ **Надбавка берётся по ОБЛАСТИ, а не по имени НП.** Сопоставление по имени (`REGION_SURCHARGE[name]`) — только запасной путь, когда сам регион не распознаётся как округ (терминалы с регионом «Россия» или названием города). Раньше оно срабатывало всегда, и 26 сёл с именами городов-исключений получали чужую ставку (Курган в Саратовской области — 0% вместо 20%, Севастополь в Оренбургской — 30% вместо 20%). Тест [calculator-districts.test.ts](test/calculator-districts.test.ts) проходит по всему справочнику и сверяет 169 терминалов со снимком `test/fixtures/calculator-terminal-surcharges.json`. Надбавка зашивается в `Direction.surcharge` в `config.ts` при сборке `DIRECTIONS`; для НП — в `/api/places` (по области НП).
- **`finalizePrice(base, surcharge)`** в [engine.ts](lib/calculator/engine.ts) — общий хвост во ВСЕХ режимах: ×(1+доля) от округлённой базы → пол `MIN_PRICE_KZT` (90 000 ₸, [config.ts](lib/calculator/config.ts)). Флаги `surchargeApplied`/`surchargePct`/`minApplied`/`basePrice` для `ResultPanel`.
- **Пресеты** (в UI называются «Шаблоны» / KK «Үлгілер» — final-improves; в коде/API/БД остаются `preset`/`CargoPreset`/`/api/presets`) (improves2.0) — считаются ТЕМ ЖЕ движком, что и «Свой груз»: пресет даёт только габариты+вес, цена = `calcShipment` по кривым ПЭК + надбавка области → поэтому пресет и «Свой груз» с одинаковыми размерами дают ОДИНАКОВУЮ цену. Поле `CargoPreset.basePrice` в БД больше НЕ используется для расчёта (оставлено в схеме, в UI скрыто). Цена доставки за единицу на карточках убрана. **Не путать с `goodsPrice`** — это себестоимость самой техники (ПРАВКИ 2 п.1), на расчёт доставки не влияет, см. §11.
- **Шаблоны берутся через `repos.presets`** ([lib/data/repos.ts](lib/data/repos.ts)), не прямым `fetch('/api/presets')`. БД-модель `CargoPreset`, сид `DEFAULT_PRESETS` ([lib/calculator/presets.ts](lib/calculator/presets.ts)). Сид: `/admin/presets` → «Загрузить стандартные» или `node scripts/seed-presets.mjs`.
- **Миграции и деплой** — в проекте Prisma-миграции (`prisma/migrations/`), все написаны идемпотентно (`IF NOT EXISTS`). Build-команда — `node scripts/deploy-migrate.mjs && next build`. Скрипт ([deploy-migrate.mjs](scripts/deploy-migrate.mjs)) гарантирует, что схема БД соответствует коду, **или валит сборку** — чтобы на прод не уехала версия, где раздел падает с 500 из-за отсутствующей таблицы. Порядок: расчистка истории от незавершённых миграций (иначе P3009 блокирует все следующие) → baseline существующей db-push базы (иначе P3005) → `migrate deploy` → **проверка наличия нужных таблиц/колонок** (`REQUIRED_TABLES` / `REQUIRED_COLUMNS` — дополнять при новых миграциях!) → если что-то не так, прямой прогон SQL через `prisma db execute` (не берёт advisory-lock, поэтому проходит через пулер) → повторная проверка → `exit 1`, если не сошлось. **Новое изменение схемы: `prisma migrate dev --name ...` локально → дописать объекты в `REQUIRED_*` → коммит → деплой применит сам.** НЕ использовать `db push` для прода.
  - ⚠️ **Build Command в самом Vercel должен быть `npm run build`.** До 2026-09-06 в настройках проекта стоял **Override** с `npx prisma generate && next build` — он подменяет скрипт из `package.json`, поэтому `deploy-migrate.mjs` на проде **не запускался ни разу**. Итог: миграция `add_notification` не применилась, `GET /api/notify` отвечал `P2021: table public.Notification does not exist`, модалка уведомлений молча уходила в ручной режим — а сборка при этом была зелёной, потому что проверять схему было некому. Вся защита этого скрипта существует ровно до тех пор, пока Vercel действительно его вызывает: при странностях со схемой на проде **сначала смотреть Settings → Build & Deployment → Build Command**, а не логи миграций.
  - ⚠️ **BOM в `20260524120000_init/migration.sql`**: из-за него `migrate deploy` падает с `P3018` / `42601 syntax error at or near "﻿"` на любой базе, где init ещё НЕ применена (т.е. на новой БД). Файл править нельзя — Prisma сверяет контрольную сумму применённых миграций, и правка сломает деплой на прод-базе. Скрипт обходит это временной копией без BOM.
  - ⚠️ **`.env` vs `.env.local`**: приложение и `deploy-migrate.mjs` берут `DATABASE_URL` из `.env.local` (приоритет, как у Next); голый `prisma` CLI — из `.env`. Явный override для тестов/CI — `DEPLOY_MIGRATE_DB_URL`. Симптом «не та БД»: `GET /api/presets` → **500** (`P2021: table ... does not exist`).
  - Если прод-БД за пулером (pgbouncer, порт 6543) — можно задать `DIRECT_URL` (прямое подключение, 5432) для `migrate deploy`; без неё сработает фолбэк на `db execute`.

### 11. Накладные (ПРАВКИ 2)

- **Хранение в БД.** До ПРАВОК 2 мастер «Создать накладную» жил только в демо-песочнице (sessionStorage) и в БД уходил урезанный `Cargo` — реквизиты терялись, накладную нельзя было открыть заново. Теперь есть модели `Waybill` + `WaybillItem`, раздел `/admin/waybills` (список → открытие → правка → удаление) и `WaybillRepo` в слое данных ([lib/data/types.ts](lib/data/types.ts)). Компоненты формы — [components/waybill/](components/waybill/).
- **Просмотр отдельно от редактирования** (как в грузах): `/admin/waybills/[id]` открывает read-only карточку [WaybillDetailPage.tsx](components/pages/WaybillDetailPage.tsx), «карандаш» ведёт в мастер. Режим живёт в адресе (`?edit=1`), а не в state — тогда «Назад» в браузере возвращает из правки в карточку, а не в список; «Сохранить» в режиме правки тоже возвращает в карточку (тост переносится через `sessionStorage['pendingToast']`). Сводка логистам показывается только у сохранённой накладной: у новой она собиралась из пустой формы и выглядела сломанной («0,000 м³, 0 тенге»).
- **Модель формы** — [lib/waybill/model.ts](lib/waybill/model.ts) (вложенные `sender`/`receiver`/`positions`); плоские колонки БД ↔ модель конвертирует [lib/mapWaybill.ts](lib/mapWaybill.ts). `waybill.docId` — cuid записи, `waybill.number` — человеческий номер.
- **Одна накладная = один груз.** При сохранении [lib/waybill/cargoSync.ts](lib/waybill/cargoSync.ts) создаёт/обновляет `Cargo` (`trackingId = CARGO-<номер>`, `cargoNumber = номер`). Статусы — РАЗНЫЕ оси: документ (`draft|active|delivered|cancelled`) и перемещение (`ожидает отправления|в пути|прибыл`). Переносится только `delivered → прибыл`; `currentCity` и «в пути» ведёт логист в `/admin`, накладная их НЕ перезатирает. Груз виден на своей карточке блоком «Накладная» ([CargoWaybillBlock.tsx](components/admin/CargoWaybillBlock.tsx)).
  - **Накладная из карточки груза привязывается к ЭТОМУ грузу:** кнопка в блоке ведёт на `/admin/waybills/new?cargoId=<docId>`, `POST /api/waybills` принимает `cargoId` и вместо нового `CARGO-<номер>` связывает накладную с существующим грузом (`cargoNumber` = номер накладной). Груза нет или он уже привязан к другой накладной — `400`. `cargoId` читается из `window.location`, а не `useSearchParams`: страница статическая, и `useSearchParams` потребовал бы Suspense.
  - Накладная, созданная сразу «доставленной», получает груз «прибыл» с `currentCity` = город получателя (только при создании; дальше город ведёт логист).
  - Если синхронизация груза упала, накладная всё равно сохраняется, но клиенту НЕ пишем (в сообщении ссылка на несуществующий груз): `notified = {status:'skipped', code:'NO_CARGO'}`.
  - Каждое сохранение накладной перезаписывает у связанного груза имя, города, даты, сумму и номер — ручные правки этих полей на карточке груза перетрутся. Отменённая накладная статус груза не меняет: в публичном трекере такой груз выглядит обычным.
- **Номера — только с сервера.** `POST /api/waybills/number` делает атомарный `INSERT … ON CONFLICT DO UPDATE … RETURNING` по таблице `WaybillCounter` ([lib/waybill/number.ts](lib/waybill/number.ts)). Раньше счётчик жил в `sessionStorage` у клиента → два оператора получали один номер. Номер резервируется при ОТКРЫТИИ формы (решение заказчика), поэтому в нумерации возможны пропуски, если форму закрыли без сохранения. Первый номер — 3000 (1–2999 заняты). **Каждая** выдача берёт `GREATEST(счётчик, MAX(Cargo.cargoNumber), MAX(Waybill.number)) + 1` в том же атомарном запросе: раньше максимум учитывался один раз, при миграции, и номер, вручную вписанный в груз, позже выдавался накладной — по ссылке `/?id=` клиент мог увидеть чужой груз. Номера ≥ 1e9 игнорируются (защита int32).
- **Повтор сохранения не создаёт дубль.** Если первый `POST` записал накладную, а ответ потерялся (таймаут, обрыв), повторное «Сохранить» приходит с тем же номером. Сервер узнаёт повтор (тот же номер + телефон получателя + ФИО отправителя и получателя, создана < 30 мин назад) и возвращает уже сохранённую накладную с кодом **200**, без второго уведомления клиенту. Другая накладная с этим номером (настоящая коллизия) → новый номер и `201`, как раньше.
- **PATCH — полная замена**, поэтому тело без `status` или без массива `positions` отклоняется (`400`): раньше такой запрос молча делал черновик и удалял все позиции. Предыдущий статус читается внутри транзакции с блокировкой строки — два одновременных сохранения «черновик → активна» уведомляют клиента один раз.
- **Валидация (ключи `wv*`):** страны отправителя/получателя, дата приёма, хотя бы одно место с весом или габаритами (или ручной объём), никаких отрицательных чисел. Сумма 0 допустима. Проверка — гейт «Сохранить» (переходы между шагами свободные): ошибка возвращает на нужный шаг. Сервер дополнительно зажимает числа в 0…1e12, округляет количество до целого ≥ 1, режет длинные строки (300 / 100 / 2000) и подставляет страну по умолчанию, только если поле отсутствует, а не очищено. Старые накладные без даты приёма или с пустыми позициями при правке потребуют дозаполнить.
- Дата приёма по умолчанию — **локальная** (`date-fns format`), а не `toISOString()`: в Алматы с 00:00 до 05:00 та давала вчерашнюю дату.
- **Печатная форма** — [lib/waybill/print.ts](lib/waybill/print.ts): логотип `/logo-ltt-ntk.svg`, реквизиты и контакты из [lib/waybill/company.ts](lib/waybill/company.ts) (единственное место для правок; пустые поля не печатаются), обобщённое описание груза, строка о соответствии упаковки, дата отправки и сроки, печать организации. Открывается в новом окне: картинки подставляются АБСОЛЮТНЫМ URL (окно — `about:blank`, относительный путь не разрешится), печать вызывает сам документ по `load`.
  - ⚠️ **Всё, что попадает в документ, проходит через `esc()`** (включая сроки, даты, статус и запасную ветку `ru()`): окно печати — того же происхождения, что и админка, и неэкранированное поле исполнилось бы с сессией админа. `buildHtml`, `esc`, `ru`, `timeframe`, `placesCount` экспортируются как чистые функции и покрыты [print.test.ts](test/print.test.ts).

  - ⚠️ **Автотест печати в Playwright зависает,** если не заглушить `window.print`: документ вызывает его по `load`, в браузере с окном открывается системный диалог и блокирует страницу. Перед проверкой — `context.addInitScript(() => { window.print = () => {} })` и таймауты на каждый шаг.
  - **Груз описывается обобщённо** (правка заказчика): характер груза + мест/вес/объём. Наименования позиций («Квадроцикл 400 куб. см») и себестоимость товара в документ НЕ попадают — это внутренние данные, они остаются в сводке логистам.
  - **`@page { margin: 0 }` + поля через `padding` на `body`** — иначе Chrome печатает в полях свои колонтитулы (URL, дата, «Стр. 1 из 1»), чего заказчик не хочет. Не менять на `@page margin`.
  - **Строго одна страница** (жалоба заказчика: документ уезжал на два листа). Держится тремя вещами, по отдельности ломать нельзя:
    1. `body { width: 210mm }` — вёрстка на экране совпадает с печатной, только поэтому скрипт может честно измерить высоту (при ширине окна 880px измерения врут);
    2. компактные вертикальные отступы — замеренный запас: обычная накладная **52 мм**, «тяжёлая» (компания + ИИН + длинные адреса + 6 позиций) **30 мм**. Добавляете строки в документ — перепроверьте запас;
    3. `fit()` перед печатью: если содержимое всё же выше листа, `#page` получает жёсткую высоту, а `#sheet` — `transform: scale(k)` (не ниже 0.78) с компенсацией ширины. Вторая страница становится невозможной, ничего не обрезается. **Высоту вешать на обёртку `#page`, а не на `body`**: у `body`/`html` переполнение пробрасывается на вьюпорт и Chrome всё равно добавлял лист.

- **Себестоимость товара в шаблонах** (п.1) — `CargoPreset.goodsPrice`, ₸ за единицу. Задаётся в `/admin/presets` («Стоимость товара»), НЕ влияет на цену доставки. Попадает в позицию накладной при «Скопировать в накладную» и в строку `Стоимость - N тенге` сводки логистам (формат — по заявке заказчика №2782). Клиентам не отдаётся: публичный `GET /api/presets` без сессии подставляет `goodsPrice: 0`, поэтому в открытом калькуляторе её нет. У существующих шаблонов значение 0 — заполняется вручную в админке.
- **БИН и банковские реквизиты в накладной не печатаются** — решение заказчика.

### 12. Уведомление клиенту: WhatsApp (SMS убран)

Кнопка «Уведомить клиента» на шаге 3 мастера. Код — [lib/notify/](lib/notify/), UI — [NotifyModal.tsx](components/waybill/NotifyModal.tsx), API — `/api/notify` и `/api/notify/webhook`.

- **⚠️ SMS из проекта убран целиком (2026-10-21, решение заказчика).** Раньше был каскад WhatsApp → SMS (SMSC / smsgate / httpsms / InfiniReach), досылка по вебхуку и по таймауту через `/api/notify/sweep`. Удалены: `lib/notify/sms.ts`, роут `sweep`, второй (короткий) текст, `fallbackToSms`, env `SMS_*`, `SMSC_*`, `HTTPSMS_*`, `INFINIREACH_*`, `NOTIFY_SWEEP_SECRET`, `NOTIFY_WA_TIMEOUT_MIN`. **Следствие, о котором надо знать:** если WhatsApp не сработал (у номера его нет, аккаунт ограничен, клиент в РФ с заблокированным WhatsApp), клиент **не получит ничего**, пока оператор не свяжется с ним сам. Модалка и тост показывают причину (`BAD_CONTACT` «У номера нет WhatsApp», `DELIVERY_FAILED`), но у Green-API и у клиентов с заблокированным WhatsApp статус навсегда остаётся `sent` — об этом узнаёт только оператор от самого клиента. Колонки `Notification.smsText`, `fallbackOf` и старые строки с `channel='sms'` оставлены как история (миграции на удаление нет; `smsText` по-прежнему в `REQUIRED_COLUMNS`). Cron на VPS, дёргавший `/api/notify/sweep`, надо отключить.
- **Провайдеров WhatsApp два, выбор в [whatsapp.ts](lib/notify/whatsapp.ts)** (`WHATSAPP_PROVIDER`): **Green-API** — целевой, облачный, номер привязан к их инстансу по QR; **WAHA** — прежняя схема на своём VPS, оставлена, чтобы переезд не ронял прод. Переключение переменной, не деплоем.
- **⚠️ Подтверждение доставки у провайдеров устроено ПО-РАЗНОМУ.** У WAHA статус можно опросить сразу (`messageAck` читает историю чата). У Green-API — нельзя: журнал сообщений отстаёт до двух минут, документация отправляет за статусами в вебхук `outgoingMessageStatus`. Поэтому рубежей два: **синхронный** `confirmDelivery` (только там, где провайдер это умеет) и **вебхук** (статус «не доставлено» пишется в журнал, оператор видит его в окне уведомления).

- **Почему WAHA, а не официальный Cloud API.** [WAHA](https://waha.devlike.pro/) — self-hosted контейнер `devlikeapro/waha`, подключается к WhatsApp как WhatsApp Web по QR. Номер компании (8 708 703 77 11) остаётся у компании, приложение WhatsApp Business на нём продолжает работать, верификация Meta и утверждение шаблонов не нужны. С версии 2026.6.1 бесплатен целиком (подписка Patreon $5/мес — только поддержка автора). Плата за выбор: это неофициальный путь, то есть нарушение правил Meta — номер теоретически могут заблокировать.
- **⚠️ WAHA не живёт на Vercel** — это Docker, нужен VPS. Приложение обращается к нему по сети, поэтому `WAHA_URL` должен быть доступен из окружения приложения; если контейнер смотрит в интернет, ключ (заголовок `X-Api-Key`) обязателен. Три параметра запуска, которые легко упустить:
  - `-v …:/app/.sessions` — **без тома сессия теряется при перезапуске** контейнера, и QR приходится сканировать заново;
  - `WHATSAPP_DEFAULT_ENGINE=NOWEB` — движок без headless-браузера (~200 МБ против 1–1,5 ГБ у WEBJS по умолчанию); на VPS с 1 ГБ RAM WEBJS не запускается. `check-exists` работает на всех движках;
  - переменная ключа у контейнера — `WAHA_API_KEY` (в старых версиях `WHATSAPP_API_KEY`). Не путать с одноимённой переменной приложения: у него это ключ, который он подставляет в `X-Api-Key`.
- **Канал выбирается ДО отправки, синхронно.** У WAHA есть `GET /api/contacts/check-exists?phone=&session=` → `{numberExists, chatId}`. Поэтому [send.ts](lib/notify/send.ts) сначала спрашивает WhatsApp про номер и только потом отправляет; «у номера нет WhatsApp» выясняется синхронно и не зависит от вебхука (у Green-API проверка недостоверна — там это приходит позже статусом `noAccount`).
  - `phone` передаётся **только цифрами**: с ведущим «+» эндпоинт отвечает 500.
  - `chatId` берём из ответа, а не собираем сами: у части номеров идентификатор приходит как `@lid`, а не `@c.us`.
  - Проверка — обращение к WhatsApp, а не локальная операция. Один вызов на уведомление безопасен, массовой проверкой номеров можно словить блокировку аккаунта.
  - Если проверка **упала** (WAHA недоступна, сессия отвалилась) — это не считается «WhatsApp нет»: уведомление помечается ошибкой, оператор видит причину.
- **⚠️ Ответ 201 на `POST /api/sendText` — это «WAHA приняла», а НЕ «клиент получил».** WhatsApp отклоняет сообщение уже после успешного ответа, и молча: 2026-08-27 аккаунт стоял под ограничением `RESTRICT_ALL_COMPANIONS` (снятая блокировка оставляет его ещё на неделю, поле `reachoutTimelock` в `GET /api/sessions/<session>`), каждое сообщение получало `error 463: account restricted` в логах контейнера и `ack = -1`, а журнал показывал «отправлено». Поэтому отправка подтверждается синхронно: `messageAck()` в [waha.ts](lib/notify/waha.ts) читает историю чата (`GET /api/<session>/chats/<chatId>/messages`) три раза с паузами 1,2 + 1,8 + 2,5 с — `ack` проставляется асинхронно, сразу после отправки там закономерно 0. `ack = -1` → строка журнала `failed` с кодом `DELIVERY_FAILED`, оператор видит причину. Это **чтение из хранилища WAHA**, а не обращение к WhatsApp: на лимиты аккаунта не влияет, в отличие от `check-exists`. Из-за ожидания у `/api/notify` и `/api/waybills` стоит `maxDuration = 30` — в дефолтные 10 с Vercel цепочка не укладывается.
- **Вебхук необязателен** и после появления проверки `ack` служит вторым рубежом — для случаев, когда статус проставился уже после ответа оператору. Он нужен для статусов «доставлено / прочитано» (событие `message.ack`, `ack`: −1 ERROR … 3 READ). Настраивается **на стороне контейнера** (`WHATSAPP_HOOK_URL`, `WHATSAPP_HOOK_EVENTS=message.ack`, `WHATSAPP_HOOK_HMAC_KEY`), а не из приложения — никакой авторегистрации подписки в коде нет. `ack = -1` (сообщение приняли, но доставить не смогли) помечает строку журнала `failed`; уже доставленное/прочитанное назад не откатывается.
- **Роут вебхука закрыт, иначе 404.** Он публичный, поэтому: либо HMAC-подпись тела (`X-Webhook-Hmac`, sha512, ключ `WAHA_HOOK_HMAC_KEY`) — предпочтительно, сравнение постоянного времени; либо секрет в query (`NOTIFY_WEBHOOK_SECRET`). Ничего не задано → 404, как будто роута нет: открытый вебхук позволил бы кому угодно менять статусы отправок.
- **Поиск строки журнала по id сообщения** ([webhook/route.ts](app/api/notify/webhook/route.ts)) — сначала точное совпадение `providerId`, потом по хвосту после последнего `_`: движки WAHA (WEBJS/NOWEB/GOWS) отдают id в разной форме, и ответ на отправку может отличаться от того, что приходит в `ack`.
- **Ручной режим — не заглушка, а рабочий путь.** Провайдер не настроен → `notifyClient` возвращает `status: 'manual'` и ссылку `wa.me`, кнопка меняется на «Открыть WhatsApp», отправку подтверждает оператор. Модалка спрашивает, настроен ли WhatsApp, **при открытии** (`GET /api/notify`, флаг берётся из `whatsappConfigured()` — он учитывает оба провайдера), а не после первого клика — иначе первое нажатие уходило бы вхолостую. Ручной режим работает и для несохранённой накладной; автоотправке нужен `docId` (по нему пишется журнал).
- **Шаблон редактируемый.** Модалка подставляет шаблон ([message.ts](lib/notify/message.ts): маршрут, мест/вес/объём, срок, сумма), но оператор может его поправить перед отправкой; `POST /api/notify` принимает `text`. Пустая правка игнорируется (уйдёт шаблон — иначе `Ctrl+A, Delete` отправил бы клиенту пустоту), длина ограничена 4096 символов, а правки живут только в открытом окне: при следующем открытии снова шаблон, чтобы вчерашняя правка не уехала новому клиенту.
- **Текст сообщения русский и в i18n не заводится** — по той же причине, что PDF (§11): это документ для клиента, а не интерфейс оператора; получатели — физлица в РФ. Телефон берётся из `COMPANY.departments`, чтобы номер в уведомлении и в PDF не разошлись. Интерфейс модалки, наоборот, целиком на `t()` (ключи `nm*`).
- **⚠️ [lib/waybill/totals.ts](lib/waybill/totals.ts) — не косметика.** `model.ts` импортирует `react-phone-number-input` (для `isPhoneValid`), а этот пакет при вычислении модуля в серверном рантайме падает с `Super expression must either be null or a function`. Роут `/api/notify` собирает текст теми же формулами, что UI, и отдавал **500**, пока итоги/форматтеры (`totalWeight`, `effectiveVolume`, `fmtMoney`, …) не переехали в `totals.ts`. `model.ts` их реэкспортирует, поэтому старые импорты работают. **Правило: серверный код берёт эти функции из `totals.ts`, а не из `model.ts`.** (`mapWaybill.ts` не страдал: он импортирует из model только типы.)
- **Журнал `Notification`:** одна отправка = одна строка, в модалке видно историю и причину неудачи (код + текст ошибки). Статусы не откатываются назад (`pending < sent < delivered < read`) — вебхуки приходят без гарантии порядка.
- **⚠️ Дедупликации отправки у провайдеров нет**, поэтому она сделана на своей стороне: `notifyClient` отклоняет повторное уведомление по той же накладной, если успешное уже уходило за последние 10 минут **или отправка идёт прямо сейчас** (`RESEND_GUARD_MS`, код `RECENTLY_SENT`). Проверка и создание строки журнала идут в одной транзакции под `pg_advisory_xact_lock` по id накладной: раньше проверка не видела строку `pending` (а отправка длится 3–10 с) и не была атомарной — две вкладки или автоуведомление вместе с кликом слали клиенту два сообщения. Строка `pending` старше 2 минут считается мёртвой: закрывается как `failed` (`TIMEOUT`) и больше не блокирует.
- **Автоуведомление — только при ПЕРВОЙ активации** ([auto.ts](lib/notify/auto.ts)): новая накладная сразу «активна» или переход «черновик → активна». Возврат в «активна» из «доставлена»/«отменена» клиенту не пишет. Отправка ждётся внутри запроса сохранения, но с общим дедлайном 20 с (`autoNotifyWithDeadline`) — ответ на сохранение всегда приходит раньше `maxDuration = 30`.
- **Таймауты провайдеров** ([http.ts](lib/notify/http.ts)): каждый запрос к WAHA/Green-API — 8 с (включая чтение тела), опрос `ack` — 3 с на попытку, подтверждение доставки — не дольше 24 с от начала отправки. Таймаут — обычная ошибка с кодом `TIMEOUT`. Раньше зависший, но принявший соединение провайдер держал запрос до 504 Vercel — а накладная к тому моменту уже была записана, и повторное «Сохранить» плодило дубль.
- **`POST /api/notify` проверяет телефон** так же, как автоуведомление (`looksLikePhone` в [links.ts](lib/notify/links.ts), E.164): иначе `400`.
- **Модалка из мастера правки знает о несохранённых изменениях** (`dirty`: сравнение с последней сохранённой копией). Сервер собирает текст И ТЕЛЕФОН из БД, поэтому при несохранённой правке автоотправка отключается с предупреждением «Сохраните накладную — иначе уйдут старые данные»; ручной режим `wa.me` работает с текущими значениями формы.
- **Ошибки в интерфейсе переводятся по коду**, а не показываются русской строкой сервера: [notifyErrors.ts](components/waybill/notifyErrors.ts) сопоставляет `code` → ключ `ne*` (в т.ч. строки журнала вида `КОД: сообщение`). Новый серверный код → добавить его туда, иначе казахский оператор увидит русский текст.
- Модалка — полноценный диалог: Esc (кроме момента отправки), фокус-ловушка, крестик заблокирован на время отправки, поздний ответ не закрывает уже переоткрытое окно.
- **⚠️ Каждое обращение к WhatsApp — риск для аккаунта, а не просто трафик.** 2026-08-26 номер компании уехал «на проверку» (24 ч, экран «Аккаунт на проверке» с формулировкой про «информацию о вашем устройстве») после серии переподключений сессии и пересозданий контейнера. Поэтому: результаты `check-exists` кэшируются на 6 часов ([waha.ts](lib/notify/waha.ts)), повторные отправки блокируются, а **сессию нельзя перезапускать и контейнер пересоздавать без нужды** — правки env лучше копить и применять одним пересозданием. Во время проверки аккаунта контейнер держать остановленным: новые попытки входа продлевают её.
- **Что делать, если аккаунт заблокировали.** Запасного канала больше нет: клиентам придётся писать вручную (с другого номера или телефона компании). Кнопка «Уведомить клиента» при ненастроенном провайдере сама уходит в ручной режим со ссылкой `wa.me`, но при настроенном, но заблокированном аккаунте показывает ошибку отправки.

- **Деньги в интерфейсе — только `formatMoney(amount, currency)`** из [format.ts](lib/format.ts): «185 000 ₸», разделители — неразрывные пробелы. Формат с точками («185.000 тенге», `fmtMoney` из [totals.ts](lib/waybill/totals.ts)) остаётся ТОЛЬКО в документах для заказчика: сводка логистам, PDF, текст WhatsApp (§11, §12).
- **«Детали оплаты» — свободный текст.** Валюта дописывается только к голому числу (`formatPaymentDetail`); раньше получалось «Оплачено 50 000 ₸ ₸».
- **Текущий город показывается, только если он отличается и от города отправки, и от города назначения** (`showCurrentCity` в [statusUi.ts](components/admin/statusUi.ts)) — в списке грузов, в папке. Иначе «Алматы → 📍Алматы → Москва» читалось как три точки маршрута.
- **Список грузов** — компактные строки: №, название, статус · маршрут, дата приёма, трек · сумма, статус оплаты. На телефоне статус и папка уходят третьей строкой, маршрут переносится словами (не обрезается), трек-номер скрыт. Скелетоны повторяют строку.
- **Детальные страницы:** «Назад» и заголовок — слева; на карточке накладной PDF / Уведомить / Редактировать — в шапке, сводка логистам свёрнута (`LogistSummary collapsible`).
- **«Клиент уведомлён?»** — `GET /api/waybills` и `/api/waybills/[id]` отдают `lastNotification {status, createdAt, error} | null` (последняя строка журнала, одним запросом на страницу — `lastNotifications` в [mapWaybill.ts](lib/mapWaybill.ts)); `NotifyBadge` показывает её в списке и на карточке. Синхронно подтверждённая WAHA доставка (`ack ≥ 2`) сразу пишется в журнал как `delivered`/`read`.
- **Публичная карточка (клиент):** цвета статусов свои (`KIND_PALETTE` в [CargoResultCard.tsx](components/home/CargoResultCard.tsx): ожидает — янтарный, в пути — оранжевый, прибыл — зелёный), в админке «в пути» синий. На телефоне маршрут — столбиком, а при показе результата (диплинк `/?id=` из WhatsApp) тёмный блок-«герой» сжимается до логотипа и переключателя языка, чтобы груз был виден сразу. Тосты на телефоне — внизу.
- **Калькулятор на телефоне:** липкая полоска с ценой внизу экрана (`StickyPriceBar`, через портал в `<body>` — иначе `transform` анимации `.ltt-fade-up` привязывал бы её к блоку, а не к экрану); в мастере накладной выключена.
- **Справочник НП дедуплицируется с терминалами по имени + коду ближайшего терминала или региону** (`dedupeSettlements` в [citySearch.ts](components/calculator/citySearch.ts)). Раньше по одному имени — и 207 настоящих НП (Железногорск в Красноярском крае, Киров в Калужской области…) нельзя было выбрать. ⚠️ **Казани нет среди 169 терминалов ПЭК** в `directions.json` — она считается как НП по ближайшему терминалу (Зеленодольск) с пометкой «примерно». Похоже на пробел в данных — уточнить у заказчика.
- **Флаги стран** в селекте — картинки (те же SVG, что у поля телефона), а не emoji: Windows emoji-флаги не рисует и показывал «KZ»/«RU» буквами. Названия стран — ключи `cn*`.
- **Неактивные кнопки** — нейтральные серые (slate/zinc, `cursor-not-allowed`), а не бледно-оранжевые.
- **Вход заблокирован после серии неудач** → страница логина показывает «Слишком много неудачных попыток… через 15 минут» (код `LOGIN_LOCKED` из `authorize()`), а не «неверный пароль». ⚠️ На локальном стенде все запросы идут с одного «IP», поэтому пять неудачных входов (свои или чужого скрипта) блокируют вход всем; счётчик в памяти — сбрасывается перезапуском dev-сервера.

### 13. Безопасность API

- **Вход** ([lib/auth.ts](lib/auth.ts)): если `ADMIN_USERNAME`/`ADMIN_PASSWORD` не заданы или пусты — вход закрыт (раньше `undefined === undefined` пускал любого без логина и пароля). Сравнение — постоянного времени по sha256. После 5 неудачных попыток с одного IP за 15 минут вход с него блокируется (даже с верным паролем), суммарно по всем IP — после 30. `getServerSession` везде вызывается через `getSession()`/`requireAuth()` с общими `authOptions`.
- **Публичный поиск груза:** точное совпадение `trackingId` (верхний регистр или как введено) — раньше `equals` + `mode: 'insensitive'` превращался в `ILIKE`, и `?trackingId=%` находил любой груз. Ввод цифрами ищется по `cargoNumber` через `safeInt` (больше int32 → 404, а не 500). Лимит — 30 запросов в минуту с IP → `429` + `Retry-After`.
- ⚠️ **Лимитеры грубые:** счётчик в памяти процесса, на Vercel он свой у каждого инстанса и обнуляется при холодном старте. IP берётся из `x-forwarded-for` — на Vercel заголовок ставит сама платформа, но за другим прокси клиент может его подделать. Для строгого лимита нужно общее хранилище (Redis/БД).
- **[lib/apiUtil.ts](lib/apiUtil.ts) — правило для новых роутов:** тело через `readJson()` (кривой JSON → 400, а не 500), `?page=` через `intParam()` (целое, зажатое до последней страницы — ответ возвращает фактическую страницу), числа из запроса в `where` — только через `safeInt()`, ошибки Prisma — `prismaErrorResponse()` (P2025 → 404, P2002 → 409, P2003 → 400).
- **Заголовки** ([next.config.mjs](next.config.mjs)): `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Permissions-Policy`, без `X-Powered-By`. CSP намеренно нет: inline-стили/скрипты Next и окно печати с inline-кодом.
- **Редиректы только внутренние:** `returnTo` на карточке груза и `callbackUrl` на логине проходят `safeLocalPath` (путь с `/`, не `//`, без `\` и схем), иначе `/admin`.

### 14. Тесты

- `npm test` — vitest, файлы `test/**/*.test.ts`. Без БД DB-тесты пропускаются (`describe.skipIf`).
- **DB-тесты гонять только на одноразовой базе:** `TEST_DATABASE_URL=postgresql://postgres@127.0.0.1:<порт>/<база>`. Хелпер [test/helpers/db.ts](test/helpers/db.ts) проверяет, что хост локальный, и подставляет `DATABASE_URL` до импорта Prisma. ⚠️ `api-presets.test.ts` очищает всю таблицу шаблонов — на рабочей базе не запускать. Схему в тестовую базу накатывать тем же путём, что и прод: `DEPLOY_MIGRATE_DB_URL=… node scripts/deploy-migrate.mjs`.
- Провайдеры WhatsApp в тестах — только моки или локальный сервер; реальные ключи из `.env.local` в тесты не попадают.
- Номера накладных, создаваемых прямо в тестах, брать **≥ 1e9**: счётчик учитывает `MAX(Waybill.number)` ниже 1e9, и тестовые номера из рабочего диапазона сдвигают нумерацию параллельных тестов (ловили коллизии).
- На Windows `pg_ctl start` может подвесить вызывающую оболочку (postgres наследует её pipe) — запускать через `Start-Process`, готовность проверять `pg_isready`.
